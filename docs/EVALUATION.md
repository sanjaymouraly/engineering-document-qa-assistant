# Evaluation

Everything in this file was produced by running the harness in this repository; nothing is
hand-written or estimated.

```bash
python scripts/run_eval.py --json-out data/eval_results.json     # fresh temporary DB
python scripts/run_eval.py --data-dir data --top-k 8              # against an existing index
```

Exit code is `0` only when every case passes, so CI fails on a regression. The harness builds a
`Service` exactly like the CLI does, runs each case through `Service.ask()` /
`Service.verify_standalone()`, and scores the result — the same code path the Streamlit UI and
`POST /api/v1/ask` use.

## Corpus

Five synthetic PDFs generated by `src/engrag/demo_corpus.py` (reportlab), each watermarked
*"SYNTHETIC DEMONSTRATION DOCUMENT — fictional data, not a real standard"*. They are invented
documents used to test the software; they are not engineering data.

| Key | File | Pages | Content that matters for the tests |
|---|---|---|---|
| TR-01 | `DEMO_transformer_TR01_manual.pdf` | 6 | nameplate table on **physical page 1** (`Rated power (ONAF) 40 MVA`, `Rated voltage 132/33 kV, ratio 4:1`, `System frequency 50 Hz`, `Vector group YNd1`, `Tap changer: OLTC on 132 kV side, ±8 × 1.25 %`), rated-quantity table on page 2 (`Maximum system voltage Um 145.5 kV`, `HV–LV impedance 12.15 %` with `±7.5 %` tolerance), losses on page 3 (`No-load loss P0 14.2 kW`, `Load loss Pk 205 kW at 75 °C`), dielectric/test data on page 4 (`33 kV LV winding … power-frequency test voltage of 70 kV`) |
| switchgear | `DEMO_switchgear_11kV_handbook.pdf` | 3 | 630 A vs 1250 A busbar sections with different short-time ratings, `43.3 kA` derived 1 s value, **a deliberately contradicting `28 kV` routine test voltage and `75 dB(A)` noise level** (TR-02 variant data in the same handbook) |
| cable | `DEMO_cable_earthing_handbook.pdf` | 3 | derating tables (`240 mm² → 254 A` at 30 °C, soil 2.5 K·m/W), and the short-circuit calculation whose last sentence reads `a 240 mm² cable is NOT adequate for a 25 kA 3 s fault; it is adequate up to 22.2 kA for 3 s` after deriving `S = 25000 × √3 / 143 = 302 mm²` |

15 pages, 29 chunks, indexed with FTS5 + the hashing n-gram vector backend.

| `num_rated_vs_max` | numeric_standalone | `145.5 kV` → `ambiguous` (that is the *maximum* system voltage, not a rated one) |
| `num_min_vs_typical` | numeric_standalone | `31.5 kA` for the *630 A* section → `mismatch` (that row belongs to the 1250 A section) |

Why the last distinction matters: TR-01 is numbered `i, 1, 2, 3, 4, 5` on six physical pages, so
an expected page can only be checked against the physical index (which the whole pipeline uses).
Documents whose printed numbering is 1..N store no label at all — the extractor skips a label equal
to the physical number, so an empty `printed_label` means “nothing different to report”, not
“extraction failed”.

The last five feed a statement written by a human (no retrieval answer involved) into
`Service.verify_standalone()` and assert the *status* the engine returns, which is what keeps the
semantics honest: a right number with a wrong scope is not a pass.

## Metric definitions (as implemented in `eval.py`)

* **Recall@k** — per case, the fraction of `expect_pages` entries whose document+physical page
  appears among the top-k evidence chunks. Missing-info cases have no expected page and are
  excluded from this average.
* **Citation accuracy** — per answered case, `citations with integrity == "ok" / all citations`,
  then averaged over cases. Integrity means: the cited chunk exists, its stored `text_sha1`
  matches, and the sentence's longest verbatim fragment was found in the chunk **and** on the page.
* **Answer support rate** — answered cases / cases that should be answerable (a `mismatch` would
  withhold an answer and lower this).
* **Abstention recall** — missing-info cases that were refused. **Precision** — 1 − (refusals on
  answerable cases / answerable cases). Both are needed: a system that always abstains scores 100 %
  recall and 0 % precision.
* **Numeric status accuracy** — expected status vs actual status for each asserted value
  (`expect_values`), across both retrieved answers and standalone statements.
* **Latency** — wall-clock `ask()` time per case; median and p95 of the 13 retrieval cases.

## What these numbers do **not** mean

* **Not general accuracy.** Five small, single-column, born-digital synthetic PDFs. Real manuals
  with multi-column layout, rotated pages, figures-as-text and 300-page tables will score lower,
  especially on extraction.
* **Not a calibrated confidence.** Recall@8 = 100 % means the expected page was in the top 8 of a
  29-chunk corpus. That is easy in a tiny corpus; it says nothing about ranking quality on
  thousands of chunks.
* **Not a latency benchmark.** All 13 retrieval cases run in one process, so the memoized
  normalized-text index and cached chunk values are warm; a cold single-user laptop may see the
  first answer take ~0.5 s, and a semantic (sentence-transformer) backend adds model load time.
* **Not an engineering sign-off.** "Verified" means "matches the cited document". The case set
  deliberately includes wrong-but-plausible statements so the *refusal* behaviour is measured —
  the harness would report a lower score if verification were weakened to make cases pass.
* **Thresholds are tuned to this corpus** (`ENGRAG_MIN_EVIDENCE_SCORE=0.10`,
  `RELEVANCE_THRESHOLD=0.02`). On a bigger or noisier corpus, retune them and re-measure; that is
  exactly why the harness is runnable in one command.

## Adding a case

```python
EvalCase(
    id="tr01_tap_range",
    question="What is the tap changer range of DEMO-TR-01?",
    kind="factual",
    expect_pages=[{"doc": "TR-01", "page": 1}],
    expect_values=[{"substr": "±8 × 1.25 %", "status": "verified"}],
    notes="nameplate row, symbol × must survive extraction",
)
```

The example above is not hypothetical: asking that question right now returns `grounded` with
five citations, all of integrity `ok`.

Append it to `CASES` in `src/engrag/eval.py` and run the harness. If a case is genuinely
answerable but the engine abstains, prefer fixing retrieval or the evidence gate over relaxing the
expectation — that is how the quote-existence and page-table issues found during development were
resolved instead of being tuned away.
